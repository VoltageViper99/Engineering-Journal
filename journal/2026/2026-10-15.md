> [!NOTE]
> **In short:** VoltOps is the app I run my repair business from. This week it learned to text customers their receipts using a private link that stops working after 30 days, and I added a way to cancel a link sent by mistake. I tried running the app in a web browser, decided it was not worth it and went back. A safety review added backups, stricter rules around money and the app's first automatic tests.

New to some of the terms? The [glossary](../../GLOSSARY.md) explains them in plain English.

## What I worked on

[VoltOps](../../projects/volt-ops.md) is the desktop app I run Voltage PC Repairs from. Between 11/10 and 15/10 it changed more than in the weeks before, so this entry covers the main points. The code was written with Claude. The requirements, the testing against real jobs and the decisions below are mine.

## What changed

- **Texted receipts (15/10).** A receipt PDF can now be sent to a customer by text. The PDF is uploaded to my business website and served at a long, unguessable link that expires after 30 days. The app itself stays on my own network. The same flow now covers cash receipts, "device ready" texts and overdue reminders.
- **Revoking and refreshing links.** A texted link could not be taken back, so a PDF sent to the wrong number would stay readable for up to 30 days. I added a revoke action, and a refresh so an edited invoice replaces the old PDF on its link.
- **A terminal front end (13/10).** A keyboard-driven second interface that runs over SSH, with the same background jobs as the desktop app, so bookings and backups keep working while it is open. It starts on boot as a user service.
- **A browser experiment, then retired (13/10 to 15/10).** I served the terminal interface in a browser behind my private proxy with a single login, and wrote the setup as a README. On 15/10 I retired it and went back to running VoltOps on the desktop only. The folder is kept as a record, and the server copy of the data is kept cold as a backup.
- **An audit pass (15/10).** I had the app checked against a list of risks and worked through them (see the decisions and lessons below).
- **Smaller features.** Customer message history, billing a job's parts and expenses onto an invoice, a job-linked cash receipt, and renaming a job's device after it is created.
- **The website side.** The business website got a small endpoint to host the receipt PDFs. I also tightened the scheduling-service worker's code in the repo. The audit notes list the steps to apply that fix, and I have not yet confirmed it is deployed.

## Problems / debugging

- **A bot filter blocked the first real send.** The upload worked in testing and failed in real use with a 403. The website's bot protection was challenging the script's default client identifier before it reached the upload function. Sending a normal identifying header fixed it, and the failure now gives a readable error.
- **Bloated PDFs.** Every invoice and receipt was close to 2 MB because a very large logo was embedded at full size. I shrink logos before embedding.
- **A service that "failed" instantly.** The terminal interface ran inside a shared tmux server, so systemd saw the command exit straight away and stopped it. Giving the service its own tmux server fixed it.
- **A browser cache showing old pages.** After an upgrade, the app's window kept showing old scripts and styles. I turned off the browser cache for the local window and noted it in the project docs.
- **Reused document numbers.** The next receipt number was worked out by counting rows, so deleting one could reuse a number and overwrite a PDF. It now works from the highest number in use.

## Decisions

- **Send a text exactly once.** Every kind of text goes through one send path that records the attempt in the database first, so a double click cannot text a customer twice. A timeout is recorded as "unknown" and blocks a resend until I have checked it.
- **Void and archive instead of delete.** Invoices and receipts that have been used are voided, and jobs are archived. The history stays, and document numbers are never reused.
- **Whole cents only, no overpayments.** The app rejects amounts that are not whole cents and payments larger than what is owed.
- **Back up before every upgrade.** A snapshot is taken before any database change at startup, and the upgrade stops if the snapshot fails.
- **Treat the scheduling worker as hostile input.** Webhooks can arrive twice or malformed, so the worker compares the secret in constant time, ignores duplicates and caps how much it returns at once.
- **Keep the app local.** I retired the server and browser deployment rather than keep a second copy of the live data to look after.

## What I learned

- A tidy-looking tool can still send the wrong thing to the wrong person, so anything that sends needs a way to take it back.
- Counting rows is not a safe way to make an identifier. Use the highest value that exists.
- A feature that works in testing can fail on the first real send because of something outside the code, like a bot filter. Test the real path once.
- The app had no automated tests until this week. Adding about a hundred showed how much I had been relying on checking by eye.
- An experiment is allowed to end. I wrote the browser setup properly, used it, and decided it was more to look after than it was worth.

## Next steps
