## What I worked on

Writing down how the homelab got to its current shape. The journal only starts on 26/09, but the lab has been in Git since 19/07. This entry covers the major changes, not every commit, and the last pieces of the 04/10 hardening day that [the main entry](2026-10-04.md) did not cover. Overview: [Homelab](../../infrastructure/homelab.md).

## What changed

### How it grew

- **July:** the first service was network-wide DNS filtering, and the infrastructure repository started the next day. From then on each service group has been its own Compose stack kept in version control.
- **August:** more stacks for media and music management, and a self-hosted file-sync service (Nextcloud) added to replace the old file share.
- **September:**
  - Synced the repository with what was actually running on the server, because the two had drifted apart.
  - Added a small business database with a read-only browser, then the signing and licence services behind [Supporter Invoicing](../../projects/supporter-invoicing.md).
  - Set up a cold-standby copy of those services on a second machine, so the product site keeps working during planned server maintenance. It is deliberately manual: only one copy ever runs, because two machines cannot safely write to the same databases. It does not cover a crash.
  - Brought in opt-in automatic updates ([26/09](2026-09-26.md), [29/09](2026-09-29.md)).
- **Early October:** the private reverse proxy ([03/10](2026-10-03.md)), then the audit and hardening day ([04/10](2026-10-04.md)).
- **Throughout:** I removed tools as readily as I added them once something was redundant. A self-hosted Git service, a second dashboard, a Docker management tool and two music helpers have all gone. Each removal also meant cleaning up its volumes, proxy route, firewall rules and docs.

### The end of 04/10

- **Immich and Nextcloud behind the proxy.** Both now have private names with their own logins, and their direct ports are bound to loopback. Nextcloud got a post-install checklist (scheduled background jobs, HSTS and the admin-page warnings), written as a README I can follow again.
- **Home Assistant stays Tailscale-only, on purpose.** It has no firewall rule for the home network. It is reached over Tailscale and has its own login on top. If a device that cannot run Tailscale ever needs it, I will add one narrow rule then, not now.
- **A repeatable, read-only audit checklist.** It has three parts: checks on the server (SSH, listening ports, firewall and Docker policy, secrets not in Git and file permissions, pending updates), a port scan from another machine, and a manual check of accounts and cloud settings. Each check says what to expect, and the file ends with a dated audit log.

## Problems / debugging

- **The audit caught my own mistake.** After I set two data-viewer pages to loopback in their compose files, a re-scan from another machine still found them open on the home network. The files were right, but the containers had never been recreated, so the old ports were still published. I recreated them and the scan came back clean.
- **Known gaps recorded, not hidden.** The first run also recorded that several containers use `:latest` tags and some run as root. Neither is fixed yet. The checklist tracks them so the count goes down over time.

## Decisions

- **Put the checklist in the repository, with expected results.** An audit I can re-run after any change is worth more than a one-off review. If a result differs, it is either a deliberate change (update the file) or a finding.
- **Scan from outside.** Checking on the server shows what the host thinks it exposes. A scan from another machine shows what a neighbour on the network would see.
- **Keep one service Tailscale-only.** It is the narrowest option, and it is written down as a decision so it does not look like an oversight later.
- **Delete things that are redundant.** Every running tool needs patching, monitoring and documenting.

## What I learned

- **A change in a file is not a change on the server.** The same lesson as the [website deploy that failed quietly](2026-10-12.md): check what is actually running, from the outside.
- **A hardening day needs a way to prove the result later.** Writing the audit as commands with expected output means I can repeat it without remembering what I did.
- **Write down deliberate exceptions**, so they are not mistaken for mistakes.
- **Drift happens when the repo and the server are both edited.** Syncing them early, and pulling before pushing, avoids untangling it later.

## Next steps

- Pin image versions where a service has a stable tag, and reduce the containers that run as root, noting the reason for any that must.
- Re-run the audit after the next service is added.
- Move the remaining services behind the proxy, one at a time.
