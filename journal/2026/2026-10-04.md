## Work completed

- Added a self-hosted design tool as its own stack, reachable only by name over the private network and never published to the internet. Its secrets live in a git-ignored environment file, and the setup is written as a README walkthrough I can follow from a clean state.
- Retired Portainer. Uptime Kuma and Dozzle already cover health and logs, so it was one more administrative interface for little value. I removed it from the compose file, the docs and the ignore rules, then cleaned up what the compose change leaves behind on the host: the container, its data volume, its image and its firewall rules.
- Finished the media stack's move behind the proxy by closing its direct host ports. The apps now reach each other by container name, and the few ports that remain are bound to the host's loopback only. Browsers and phones use the proxied names. I removed the firewall rules that only existed for the old paths.
- Installed the secret scanner on the server. The commit hook refused to run until I did, which is the intended behaviour.
- Brought the server's copy of the infrastructure repo back in line with the remote after it had fallen behind.
- Audited what the server actually exposes: listening ports, firewall rules, the Docker firewall policy and the SSH settings. The result is recorded as a baseline in the infrastructure repo.
- Hardened SSH. It now accepts keys only, refuses root logins, allows fewer attempts per connection and is watched by fail2ban. It is reachable from the home network and over Tailscale only.
- Narrowed the firewall. The widest rules, for SSH, file sharing and UPS status, now allow only the home network and the containers that need them. I also removed the matching IPv6 rules, since the host has no public IPv6 address.
- Bound two data-viewer pages that have no login to the host's loopback, because they show business records and I never open them from other machines.
- Protected the log viewer, which can read every container's logs. I turned on its built-in login with a hashed password in a git-ignored file, then put it behind the private proxy so the login is encrypted, and finally closed its direct port to the network. The monitor now reaches it by container name.

## Architecture / decisions

- **Repoint first, close second.** The apps pointed at each other through the host's address and published ports. I changed those links to container names while the old path still worked, tested them, and only then closed the ports. The change is easy to undo because the old path comes back immediately.
- **Loopback, not removal.** Binding a port to loopback keeps anything running on the host itself working, while no other machine can reach it.
- **Login first, then TLS, then close the port.** Each step was verified before the next. A login over plain HTTP only stops casual browsing, so the proxy step was worth doing, and closing the old port is what makes the encrypted path the only one.
- **Monitors use container names too.** The proxy deliberately answers only LAN and Tailscale sources, so a monitor running in a container cannot use the proxied names. Container names over the shared network are the right path for it.
- **The README carries the order of steps.** The repo can hold the compose change, but the app settings live inside each app's own database. The README walkthrough covers that part, with checks and a rollback.

## Why

- Every direct port is exposure that has to be justified. Proxying a service does not close its original port, so the two have to be done as separate steps.
- Portainer had broad control over Docker. An administrative tool with that power should earn its place, and this one did not.
- Fewer tools means fewer things to patch, document and monitor.

## What I learned

- Finding what depends on a port takes more than searching the repo. The real consumers are settings inside the apps, so I checked those by testing each link rather than assuming.
- Test the actual connections between apps, not just that the port is now closed. A closed port tells you nothing about whether the apps still work.
- Removing a service means removing its leftovers: the container, volume, image, firewall rules, docs and ignore entries. Deleting the compose block only removes the definition.
- Two copies of a repo drift apart. When the server and my other machine both edited the same file, the fix was to pull first and keep one version of each change.
- A hook that fails closed is annoying exactly once, and that is the point.
- Shell differences bite in setup docs. A password prompt that works in bash fails in zsh, so the README now shows both. Test copy-paste commands in the shell they will actually run in.
- A container's published port can differ from the port the app listens on inside. The logs said what the app really listened on, and the mapping had to match it.
- Audit before hardening. Listing what really listens found exposure that reading the repo could not: pages with no login, a log viewer open to the whole network, and host services bound to every address.
- Docker-published ports bypass the host firewall, so two separate policies decide who reaches what. Knowing which gate applies to a service is the first question to ask.
- Before changing SSH, prove key login works and keep a second session open. Test each change from a new connection, and add a narrow rule before deleting the wide one.
- "Bound to every address" means "the whole network". A service with no login belongs on the loopback.

## Next

- Decide how to protect or close the remaining utility pages that have no login. The log viewer is done; a power-status page, a notification service and a browser-automation helper are left.
- Keep moving the remaining services behind the proxy, one at a time, checking dependencies before touching any port.
- Look at the services that still publish direct ports, starting with the ones that have no special reason to.
