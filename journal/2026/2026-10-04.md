## What I worked on

A long day in three parts: retiring Portainer and finishing the media stack's move behind the proxy, auditing what the server actually exposes, and hardening what the audit found.

## What changed

### Cleanup and migration

- Added a self-hosted design tool as its own stack, reachable only by name over the private network and never published to the internet. Its secrets live in a git-ignored environment file, and the setup is written as a README walkthrough I can follow from a clean state.
- Retired Portainer. Uptime Kuma and Dozzle already cover health and logs, so it was one more administrative interface for little value. I removed it from the compose file, the docs and the ignore rules, then cleaned up what a compose change leaves behind on the host: the container, its data volume, its image and its firewall rules.
- Finished the media stack's move behind the proxy by closing its direct host ports. The apps now reach each other by container name, and the few ports that remain are bound to the host's loopback only. Browsers and phones use the proxied names. I removed the firewall rules that only existed for the old paths.
- Installed the secret scanner on the server. The commit hook refused to run until I did, which is the intended behaviour.
- Brought the server's copy of the infrastructure repo back in line with the remote after it had fallen behind.

### Audit

- Audited what the server exposes: listening ports, firewall rules, the Docker firewall policy and the SSH settings. The result is recorded as a baseline in the infrastructure repo.

### Hardening

- **SSH.** Keys only, no root login, fewer attempts per connection and fail2ban watching. Reachable from the home network and over Tailscale only.
- **Firewall.** The widest rules (SSH, file sharing and UPS status) now allow only the home network and the containers that need them. I also removed the matching IPv6 rules, since the host has no public IPv6 address.
- **Pages with no login.** Bound two data-viewer pages to the host's loopback, because they show business records and I never open them from other machines.
- **Log viewer.** It can read every container's logs, so I turned on its built-in login with a hashed password in a git-ignored file, put it behind the private proxy so the login is encrypted, and closed its direct port. The monitor now reaches it by container name.
- **UPS dashboard.** Authentication had been switched off entirely. It now requires a login, is reached through the proxy and its direct port is closed. The stack refuses to start if the login values are missing, so it cannot come back up open.
- **Proxy logins.** The proxy adds no login itself, so each proxied name has its own strong password in a password manager.
- **Browser-automation helper.** It has no login and is called by only one other app, so it needs no public name. It joined the shared container network, the other app calls it by container name and its port is bound to loopback.
- **Push-notification service.** It had no authentication. I made denial the default, gave it a private proxied name with a login and moved its clients over: the updater and the monitor publish by container name as limited accounts, and my phone logs in over https. Then I closed its direct port.

## Problems / debugging

- **Hidden dependencies.** Searching the repo did not find what depended on each port. The real consumers were settings inside the apps' own databases, so I tested each link instead of assuming.
- **Notifier URL.** I wrote a notifier option from current documentation and the container refused to start, because its bundled library was older. Running the real image locally reproduced the error in seconds and showed the supported form.
- **Port mapping.** A container's published port differed from the port the app listened on inside. The logs showed the real one, and the mapping had to match.
- **Drifting repos.** The server and my other machine had both edited the same file. I pulled first and kept one version of each change.
- **Shell differences.** A password prompt that works in bash fails in zsh, so the README now shows both.

## Decisions

- **Repoint first, close second.** The apps pointed at each other through the host's address and published ports. I changed those links to container names while the old path still worked, tested them and only then closed the ports. It is easy to undo because the old path comes back immediately.
- **Loopback, not removal.** Binding a port to loopback keeps anything on the host itself working, while no other machine can reach it.
- **Login first, then TLS, then close the port.** Each step was verified before the next. A login over plain HTTP only stops casual browsing, so the proxy step was worth doing, and closing the old port makes the encrypted path the only one.
- **Monitors use container names too.** The proxy deliberately answers only LAN and Tailscale sources, so a monitor in a container cannot use the proxied names. Container names over the shared network are the right path.
- **The README carries the order of steps.** The repo holds the compose change, but app settings live in each app's own database. The README walkthrough covers that part, with checks and a rollback.

Why: every direct port is exposure that has to be justified, and proxying a service does not close its original port, so the two are separate steps. Portainer had broad control over Docker and had not earned its place. Fewer tools means fewer things to patch, document and monitor.

## What I learned

**On method**

- Audit before hardening. Listing what really listens found exposure that reading the repo could not: pages with no login, a log viewer open to the whole network and host services bound to every address.
- Test the actual connections between apps, not just that a port is closed. A closed port says nothing about whether the apps still work.
- Before changing SSH, prove key login works and keep a second session open. Test each change from a new connection, and add a narrow rule before deleting the wide one.
- Check the version a tool actually ships, not the latest documentation.
- Test copy-paste commands in the shell they will run in.

**On exposure**

- Docker-published ports bypass the host firewall, so two separate policies decide who reaches what. Knowing which gate applies is the first question to ask.
- "Bound to every address" means "the whole network". A service with no login belongs on loopback.
- Turning authentication off is a decision to revisit, not a setting to forget. The UPS dashboard had it disabled from the start and nothing flagged it until the audit.
- A limited account beats a shared one. The updater can only publish to its own topic, so a leaked password cannot read anything.

**On housekeeping**

- Removing a service means removing its leftovers: container, volume, image, firewall rules, docs and ignore entries.
- Two copies of a repo drift apart. Pull first.
- A hook that fails closed is annoying exactly once, and that is the point.

## Next steps

- Settle the last open question on the list, one smart-home service that only the tailnet can reach, then run a full audit of everything changed so far.
- Keep moving the remaining services behind the proxy one at a time, checking dependencies before touching any port.
- Look at the services that still publish direct ports, starting with the ones that have no special reason to.
