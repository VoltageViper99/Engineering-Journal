## What I worked on

Pulling together the three public websites I run and deploy: my repair business, a photography business and the Supporter Invoicing product site. Project page: [Business Websites on Cloudflare Pages](../../projects/business-websites.md). This entry covers the main points from late September to now, not every change.

## What changed

- **Late September:** a spam bot used the repair site's contact form, which also emails a confirmation to whatever address is typed in. I added a honeypot field, stricter server-side validation, Cloudflare Turnstile checked on the server, and per-IP rate limiting.
- **Product site:** the original source had been lost, so I recovered it from the live site, cleaned it up and put it in Git. A few days later I added an on-site sign-then-pay purchase flow and had it code-reviewed before merging.
- **Early October:** found and fixed the failed deploys described below, then replaced the repair site's "software development" page with an "Engineering" page that matches what I actually offer.
- **Photography site:** turned on Cloudflare logging.

## Problems / debugging

The protections went in on 30/09, and the form looked fine. When I tested end to end on 08/10, the new behaviour was not there. Every deploy since 30/09 had been failing: the config file held a placeholder where the real storage namespace id belonged, and Cloudflare rejected it. The static pages published and the server functions did not, so the old, unprotected form kept running for eight days.

The fix was to put the real id in the config file and redeploy. My notes had said the dashboard setting was enough, which was wrong once a config file exists. I then tested from a phone on mobile data. Repeated tests from one address trip the rate limit, so a laptop would have locked me out.

## Decisions

- **Layer the form defences and fail closed.** If a secret is missing the request is refused, rather than quietly allowed.
- **Scope the shared Turnstile widget** by checking the hostname on the server, because the same widget serves several of my sites.
- **Keep plain settings in the config file and only secrets in the dashboard.**
- **Leave preview deployments unconfigured** for now, because their temporary addresses would not pass the hostname check anyway.

## What I learned

- A merged change is not a deployed change. After any security fix I now check the live behaviour, not just the commit.
- A deploy can half succeed. Pages published while functions failed, and nothing told me.
- Config files and dashboards can disagree, and one quietly wins.
- Code that only a bot would break needs a test that behaves like a bot, from outside.

## Next steps

- Add an alert for failed deploys.
- Decide whether preview deployments need the form secrets.
