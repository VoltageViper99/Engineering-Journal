> [!NOTE]
> **In short:** I built a small website, the Voltage Business Portal, that brings my repair app, my software licences and my server status into one place behind one login. To make that work, I moved VoltOps (the repair app) off my desktop and onto the server, so it runs all the time without a window open. I rehearsed the move first on spare ports, wrote down the steps, then did the real switch. I also added a second, limited login so a helper can book jobs and send invoices without seeing everything.

New to some of the terms? The [glossary](../../GLOSSARY.md) explains them in plain English.

## What I worked on

Until this week, [VoltOps](../../projects/volt-ops.md) was a window on my desktop. That meant my phone, the server and any other person could only use it while my desktop was on and the window was open. I wanted three things: to reach it from anywhere on my own network, to let a helper do part of the work, and to see the business and the server in one view.

I used Claude to write the code. I decided what the portal shows and what it is allowed to do, chose the cutover plan, ran the real switch and checked it afterwards.

## What changed

**VoltOps**

- Can run **headless**: no window, just a small service the portal talks to.
- **Software sales.** A new job type for selling software, with a button on the job page to issue a licence by hand, and a button to text an invoice link to a customer.
- Uploads, downloads and the wording of the text messages now work from a browser as well as a desktop window.
- Test messages and test licence requests can be hidden from the lists instead of cluttering them.
- A vulnerability fix: the image library it uses was updated to a version that clears the 39 known advisories against the old one. I also restricted which image types it will open.

**The Voltage Business Portal**

- Built in five milestones in two days: the shell and login, a homepage, a customer list and profile, a Software Licences area (view, check signature, issue) and a read-only Infrastructure page.
- The portal only ever talks to the other systems **server to server**. The browser talks to the portal and nothing else.
- Later additions: a Messages page (every text sent, with failures marked "Needs attention" rather than lost), a Settings area in eight sections with a re-prompt for the password before sensitive changes, and an audit trail.
- **A helper login.** A second account that can book jobs, create invoices, text customers and see the numbers, but not the owner-only things such as bank details. I wrote the specification before writing any code.
- Continuous testing on every change (about 680 checks), exact pinned library versions, and a contract test that proves the portal still understands what VoltOps sends.

**The Control Centre** gained one small read-only status endpoint with a key that can open nothing else, so the portal can show the server's health without being given the keys to the server.

## How I did the switch

1. **Rehearse first.** I ran a copy of VoltOps and the portal on spare ports with a copy of the data, and wrote down everything that went differently from the plan.
2. **Prove the copy.** A small checking tool compares a copied data folder with the original and says if anything differs.
3. **Write the runbook.** Every step, in order, with what to check and how to go back.
4. **Switch.** Stop the desktop copy, run the real data on the server, point the internal name at the portal, check an invoice end to end.
5. **Retire the old paths.** The desktop window and the old terminal front end are gone. VoltOps is now changed by editing its settings file and restarting the service.

## Problems / debugging

- **The proxy could not reach the portal.** The portal was listening only to its own machine, but the reverse proxy runs inside a container and reaches the host from outside. Changing what the service listens on, and writing that into the runbook, fixed it.
- **A port I planned was taken.** The port I had picked for VoltOps' internal API was already used by the notification service. I found it on the rehearsal and chose another before the real switch.
- **The editor refused my settings file.** The safe way to edit a protected file would not open one that sat in a folder I own, which is a sensible refusal. The runbook now says to use a root editor and then put the owner and permissions back.
- **The server said things had "never been checked".** The Control Centre's health feed marked three parts as never checked, because the background jobs were not stamping the time. The portal showed it faithfully. The bug was in the feed, not the portal.
- **"Control Centre is unaffected" was not always true.** The portal's error page said the Control Centre was fine when the server it lives on was down as well. The message now says only what it can actually know.

## Decisions

- **Keep VoltOps and the portal separate.** The portal does not replace VoltOps. It asks it questions, and shows its answers. If the portal breaks, I can still use VoltOps.
- **Least access for the helper.** The helper account can do their job and no more, and bank details are owner-only. Tailscale was already on the helper's devices, so I did not open anything to the internet.
- **Rehearse, then switch.** Everything surprising happened on the rehearsal. That is what it was for.

## What I learned

- A rehearsal pays for itself. Every item under "Problems" above was found before the real switch except the "never checked" bug.
- "Server to server" is a useful rule: the fewer things a browser can reach directly, the less there is to protect.
- Write the specification for a second login before the code. Deciding what the helper must not see took longer than building it.
