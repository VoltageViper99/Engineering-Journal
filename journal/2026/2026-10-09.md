## What I worked on

Over about two months, [Control Centre](../../projects/control-centre.md) went from a single status screen to the tool I run the lab from. This entry is the story and the decisions. The project page is the reference. The code was written largely with Claude. I set what it had to do, tested every change against the real stack and decided how it should behave.

## What changed

- **Rewrite for reliability (September).** Replaced the first design, which relied on a separate agent over SSH, with a web service that collects data in separate background pollers. A native display client replaced the browser kiosk. A test suite arrived with it.
- **Login first (22/09).** Added login and scoped API keys, so nothing browser-facing is open by default.
- **Acting, not just watching (26/09 onward).** Added start, stop and restart for a single container, then an upgrade action that checks the container comes back healthy and can be undone once.
- **One verdict (06/10).** Rebuilt the overview as a status-first page, and added Security (Trivy scans and operating system updates), Cloudflare operations and Docker maintenance pages.
- **Hardening pass (06 to 08/10).** CSRF protection on every state-changing request, session handling consolidated, a Settings page, and security status that goes critical on the right triggers.
- **Housekeeping (07/10).** Removed dead code and merged duplicated helpers before adding more.

## Problems / debugging

- **Pages disagreeing with each other.** The kiosk and the web overview each worked out the same summary separately and could show different answers. I had the logic moved into one shared summary.
- **Stale scan results.** Trivy results kept showing containers I had already removed, so I had them pruned.
- **Upgrades that looked like they worked.** An upgrade could report success when the image had not actually changed, and the status could lag behind reality. Both needed fixing so the screen tells the truth.
- **Mobile.** It was usable on a phone but not designed for one. That is on the list rather than patched again.

## Decisions

- **Risky actions are opt-in, narrow and reversible.** One container at a time, protection levels enforced on the server, no creating or deleting containers, and a one-time undo for upgrades.
- **Log before enforce.** I switched permission tiers on in a log-only mode first, to check real traffic before anything could be denied.
- **Split music into its own app.** A failure there should never take the dashboard down.
- **Pause to clean up.** I stopped adding features to remove duplicated and dead code, because a tool I rely on has to stay understandable.

Why: this dashboard can restart things on the machine it watches. Being wrong costs more than being slow, so every action is limited and every state is shown plainly.

## What I learned

- Directing AI-written code is a real job. The useful part is a precise description of the behaviour I want, testing it on the real system and rejecting what is subtly wrong. An upgrade reporting success when nothing changed is a good example.
- Build in small branches and merge when it works on the real lab. The history is full of small merges for that reason.
- Show "Unknown" rather than a guess. A dashboard that is confidently wrong is worse than none.
- Clean-up days are part of the project, not a detour from it.
