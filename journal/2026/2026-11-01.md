> [!NOTE]
> **In short:** After a week of large changes I spent a day tidying up and fixing what had been left behind. Some of it was housekeeping, such as capping a database file that had grown to 1.7 GB. Some were real faults: a page that could not reach its service, a software licence that would not issue, and music that stopped whenever I turned off my own dev computer. I also proved that my cloud backup really restores.

New to some of the terms? The [glossary](../../GLOSSARY.md) explains them in plain English.

## What I worked on

A list, in the order I worked on it. I used Claude for the investigation and the code. For anything that needed administrator rights on the server, I ran the commands myself.

| Area | What I did |
| --- | --- |
| A file that never shrank | The dashboard's database keeps a side file for recent writes (the "WAL", a write-ahead log). Mine had grown to 1.7 GB and never gave the space back. I checkpointed it back to nothing and set a 64 MB cap so it cannot happen again. |
| The old music interface | Removed the old pages, styles and scripts now that the new player is in use. |
| Receipts from my dev machine | A **token** (a long secret that stands in for a password) that can only upload a receipt, add an expense and list expenses and categories. An AI agent on my development machine can now file receipts into VoltOps over a private tunnel. The token cannot see customers, jobs or invoices. |
| One-command deploys | An update script for the music app, and one for VoltOps and the portal. Both refuse to run as root. |
| Loose files in my home folder | Moved them into a private archive, with every move written to a log so it can be reversed. Nothing unique was deleted. I kept a key for an encrypted backup folder exactly where it was, with a note never to delete it. |
| Server maintenance scripts | Copied the watcher scripts from my home folder into a Git repository on a branch, without touching the cron copies that run them. |

## Problems / debugging

### The terminal page that could not reach the terminal

The Control Centre's terminal page said "Could not reach the terminal service". The service was running and listening. Everything else worked.

**Cause:** the reverse proxy had no route for the terminal's name. Requests to it fell through to nothing.

**Fix:**

1. **Look first.** I checked that the terminal service was up, that the dashboard knew the right address and that the proxy had no matching rule. Nothing changed during this part.
2. **Add the route.** One small block, inside the part of the proxy that only answers my own network and private network, never the public tunnel.
3. **Reload carefully.** The proxy is set up so its normal "reload" command does not work. A restart would drop every site for a moment, so I tested a graceful reload by signal on a throwaway container first.
4. **Prove it from outside.** The browser handshake for a live connection came back as accepted, the direct port to the service was refused from the network, and the other services were still up.

**The catch.** The proxy's settings file is mounted into its container as a single file. When Git replaces that file during a pull, the container keeps looking at the old one until it restarts. So after any pull that touches it, I now compare the file the container sees with the one on disk before trusting a reload.

### A merge that quietly broke the repair app

After merging the receipts-token change into VoltOps, every request it handled came back as an error. The merge had dropped one small function that checks the shape of an incoming call, and nothing complained until the first real call.

I put the function back the same day. The lesson is now a rule: **run the tests again after every merge**, not only before it.

### A deploy that would have undone itself

The Control Centre's "slimmed down" branch, with the music code removed, had never been merged on GitHub. The next deploy from the main branch would have **put the old music code back**. I merged the latest main into that branch, added the database fix on top, and had it reviewed and merged first.

### The licence that would not sign

Issuing a software licence failed with "no signing key set up for that product". The licence service signs each key with a private key held as a secret in Cloudflare, and the one for this product was missing.

I did not generate a new key, because that would have made every licence ever issued invalid. Instead I wrote a one-off script that asked for the existing key at a hidden prompt, checked that it matched the public key already published, and put it into place. I ran it myself, so the key never passed through the chat. Then I deleted the script.

While there I asked how licences are stored. Keys are emailed once as a PDF and are **not stored anywhere**, by design. A key works on one device. So if a customer loses theirs, or changes computer, all I can do today is issue a fresh one. A button to revoke and reissue is now on the roadmap.

### The Bluetooth that dropped when I turned off my computer

This one annoyed me for a while. Music played through a Bluetooth adapter on the server, and every time I shut down my development machine, the adapter disconnected and I had to reconnect it by hand.

It made no sense, because my computer and the adapter had nothing to do with each other. Here is how I narrowed it down:

1. **Not the pairing.** The adapter was paired, trusted and bonded.
2. **Not the radio.** The kernel log showed no errors.
3. **Not the user session.** "Linger" was already on, so the server keeps my services running without a login.
4. **The log lined up with my logins.** The Bluetooth service logged that the audio manager had unregistered its Bluetooth endpoints at the exact second my last remote session ended, and registered them again a second after I logged in.

The audio manager (WirePlumber) has a setting that says: only handle Bluetooth while someone is logged in at the machine. That is sensible on a laptop. On a server with no screen, the only "someone" is me over SSH from my development machine. When that machine went off, the last session ended and the manager let go of the Bluetooth device.

**Fix:** one small file in my own settings folder that turns that check off, then a restart of the audio manager. I did it myself and tested it by turning my computer off with music playing. The music kept going.

### A restore that I tested, partly

I restored from my cloud backup to prove it works. The repository opened, the latest snapshot was found and a database dump came back at its full size in ten seconds. **What I have not yet tested** is the photo restore, because my test command only asked for the database dump. That is next.

## Decisions

- **Do not generate a new key to fix a missing one.** Re-setting the same key is the safe fix. A new one would break everything already issued.
- **Keep secrets out of the chat.** Anything secret goes through a hidden prompt on the machine it belongs to.
- **Cap what grows.** A file that can grow without limit eventually will.
- **A narrow token for the agent.** The agent can do the one job I gave it and nothing more.
- **Do not fix the Bluetooth by adding something.** The cleanest fix was to switch off a check that was wrong for this machine.

## What I learned

- A fault that appears when something else happens, such as turning off my own computer, usually has a link in the logs. Line the timestamps up.
- A file mounted into a container by itself can go stale when Git replaces it. Mount the folder, or check after every pull.
- Merges can quietly drop code. Running the tests afterwards is cheap.
- "Restored" and "restored the thing I need" are different. Say which.
